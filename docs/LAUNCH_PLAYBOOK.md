# Launch and contributor outreach playbook

The goal is not to describe MooNsEvents as “everything for everyone.” Lead with one workflow,
provide proof, and give the reader one useful next action.

## The one-sentence description

MooNsEvents is an open-source event operating system that connects enquiry, runOfShow curation,
supplier RFQs, proposals, booking operations, and support in one TypeScript stack.

## Ninety-second product-showcase script

**0–10 seconds — the problem**

> A events team receives an enquiry, builds an runOfShow, asks suppliers for rates, sends a
> proposal, and operates the booking. That work usually gets split across a CRM, documents,
> spreadsheets, email, and chat.

**10–25 seconds — the connected workflow**

> MooNsEvents keeps that client production together. A lead carries its calls, messages, owner,
> notes, and follow-ups into the runOfShow and proposal process.

**25–45 seconds — runOfShow and route**

> The runOfShow is editable day by day. Teams can add activities and transport, attach locations,
> and turn the same route into a proposal-ready map or animated production.

**45–62 seconds — suppliers**

> When prices are needed, choose the RFQ scope, dates, venues, and vendors. Maya can draft the
> request, but an operator reviews it before dispatch.

**62–78 seconds — operations and guardrails**

> Packages, bookings, payments, support, and incidents stay connected. Maya's channels, tools,
> approvals, and kill switches are visible instead of hiding autonomous actions.

**78–90 seconds — call to action**

> MooNsEvents is MIT licensed. Run it locally, inspect the architecture, or take a good first issue
> in maps, accessibility, testing, setup, or integrations.

## Distribution checklist

- [ ] Publish a tagged GitHub release after CI passes on the merged commit.
- [ ] Put the product-showcase URL in the GitHub repository homepage field.
- [ ] Record the 90-second walkthrough using the script above.
- [ ] Publish one focused feature per post instead of a full feature dump.
- [ ] Ask for a specific review question.
- [ ] Reply to every useful issue, discussion, and pull request.
- [ ] Review GitHub traffic weekly and record which links or communities sent qualified visitors.
- [ ] Never scrape, mass-mail, or imply a business endorsed the project.

## GitHub traffic review

Repository owners can review **Insights → Traffic** for clones, visitors, views, and referring
sites. GitHub retains a limited window, so record a weekly snapshot with:

| Week       | Visitors | Unique clones | Top referrer | Post or activity | Useful outcome |
| ---------- | -------: | ------------: | ------------ | ---------------- | -------------- |
| YYYY-MM-DD |          |               |              |                  |                |

Judge a channel by useful outcomes—issues, discussions, trial feedback, forks, or pull
requests—not by raw impressions alone.
